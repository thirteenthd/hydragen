# Capacity, batch-slot and residency-policy arms (3090 / the reference host, 2026-11-05)

Verbatim measured arms moved out of SKILL.md 5c-5f to keep the body lean. Numbers are wall/API-based, not engine tok/s prints.

5c. MEASURED `--expert-cache-per-layer` on the 3090 at batch12 (batch12/ec3400/ctx32k, cross-domain forkbench 2 passes + forkbench_domains): N=1 61.6/61.7 (baseline 58, +6%), N=2 72.5-74.7 (baseline 77), N=4 74.5-75.3 (baseline 82), N=8 70.3-72.4 (baseline 74); code N4 79.3 / N8 74.5 (baseline 83.3/82.1 — domain-pinned flatness LOST), volcano N4 68.5 / N8 72.9 (baseline 70.0/75.6). Fill 4416 experts uniform-per-layer vs 4419 arrival-order. Verdict: on a slack-VRAM card per-layer lifts ONLY the single stream — uniform per-layer budgets evict the hot-layer over-allocation that arrival order gave pinned traffic, so N>=2 and domain-pinned aggregate regress. Adopt per-layer on the 12 GB node (measured +12.5%), not on a slack-VRAM node at high batch. Separately: batch12/ctx32768 on the 3090 hard-rejects long agent prompts — 13 logged 400s, worst 144,780-token prompt — restore ctx 200000 prod whenever you are not benching.
5d. RESIDENCY GRANULARITY MAP (verified against the full 272-line `--help`): the atomic residency unit is the **(layer, expert) blob** — at iq3_s a blob is 3x(2560x640) at 3.33 bpw = **2.04 MB** (5302 blobs = 10.09 GiB = 110 slots/layer; the whole model's MoE is 24576 blobs = 46.8 GiB). There is **no sub-expert knob** — the help contains no tile/partial/fraction/slice option for the expert cache; a blob is loaded and computed whole. Finer-than-layer exists only on other axes:
   - Placement across GPUs: `--expert-cache-remote-placement stripe|layer` distributes **expert ranks** (default, finer) or whole layers; `--expert-cache-device1..3 N|auto`; `--trim-stage-weights` = "an explicit --layer-split: each GPU loads only its own layers' dense weights".
   - Rows across GPUs: `--peer-device N` second GPU as an adaptive expert-cache tier, with `--peer-slots`, `--peer-adapt-swaps`, `--peer-prefill-rows N` (prompt rows per layer, default half of chunk x top-k) — row-level, not layer-level. Mutually exclusive with `--layer-split` / `--expert-cache-device1..3`.
   - Precision tiers of the SAME expert: `--cpu-oracle-q8-0` (CPU tier holds a re-quantized q8_0 copy), `--mtp-q4 all|proj|head`. Blob precision for the GPU tier is fixed by the `--pack` dir, and packs quantize MoE separately from dense (3080 Ti node: `hyr-id2s-strata-q4k-moe-iq3`; 3090 has only `models/packs/iq3_s`). tools/ carries the pack toolchain (iq_pack.py, nvfp4_local_pack.py, pack_index.py, nvfp4_verify.py, canonical_xcheck.py).
   - VRAM<->slot trading: `--kv-resident N` ("the freed VRAM goes to expert slots"), `--kv q4_0`, `--kv k8v4`.
   - Cost math for the capacity lever (slots/layer -> GiB at fixed ctx 200k): 3.33 bpw 150/200/250 = 13.4/17.9/22.3 GiB (does not fit); 2.5 bpw = 10.3/13.7/17.2; 1.75 bpw = 7.2/9.6/12.0; 1.5 bpw = 6.2/8.2/10.3. **To reach the ~200 experts/layer working set without shrinking ctx you must shrink the blob to ~1.7-1.8 bpw** (iq2-class or nvfp4); that is a pack build + quality measurement, not a flag flip. NVFP4 has no tensor cores on Ampere, so an fp4 pack is a staging-memory win only — which is where the bottleneck is.
   - Sub-expert spatial slicing (e.g. resident blocks of the 640-wide intermediate) is mathematically legal for SwiGLU (out = sum over intermediate columns of down[:,c] * silu(gate_c.x) * up_c.x) but is a bad trade on this engine: fragmenting blobs multiplies kernel launches, and the measured 3.8x gap is launch efficiency. Grouped-GEMM amortization rewards FEWER, BIGGER blobs with more rows each.
5e. MEASURED routing-trace residency-policy simulation (`--dump-routing` on prod batch1, 24 conversations = 8 code / 8 cross-topic / 8 volcano, 400 tokens each, then offline cache replay — scripts/capture_traces.py + scripts/sim_affinity.py + scripts/sim_partition.py). Answers "would affinity/pinning fix the N=8 collapse?" — NO, it is capacity-vs-demand:
   - qwen3.8-flash-next has 48 routing layers. One 400-token conversation touches **~200 distinct experts per layer** (of 512); 8 concurrent conversations union to **~300-330/layer**. 3090 prod residency 5302 blobs = **~110 slots/layer** -> ~3x oversubscribed before policy matters. Item 4's 47-65/layer figures are HOT-MASS pools, not window demand: per-window distinct demand at N=8 is ~56/layer, so ~110 slots/layer covers only ~72% of a window.
   - Expert loads per window at 92 slots/layer: **67 (N=1) -> 158 (N=2) -> 399 (N=4) -> 953 (N=8)** — near-linear blow-up because each row contributes 10 picks and shares only 0.4-4.8. Engine cross-check at N=1: sim 89% window coverage @110 slots/layer vs measured 93-97% routed-entry hit, +0.3-0.8% PCIe, 92-114 tok/s sequential — the simulator is calibrated.
   - Per-layer Jaccard of whole-conversation working sets: same-style pairs 0.65-0.70, code-vs-prose pairs 0.43. Domains cluster weakly; ~43% of any working set is shared with any other domain, which is why domain pinning is not free.
   - Policy scan at equal total slots (arrival+LRU / Strata-gated frequency / bundle-coverage eviction / static oracle profile / class-partitioned budget): static oracle beats LRU by only **10-22% fewer loads at 92-110 slots/layer**, 30-47% at 150-200. **Class-partitioned (pinned) budgets are WORSE than one shared cache: +31% loads at 92/layer, +101% (2 classes) to +228% (3 classes) at 200/layer, penalty growing with capacity.** Bundle-aware eviction as implemented was worse than LRU (it chases near-covered windows and destroys temporal reuse).
   - Build priority derived: (1) more slots per layer toward the ~200/layer working set (cheaper/quantized expert blobs, smaller ctx head), (2) fewer picks per row, (3) load dedupe across the rows of one window (MTP verify chains already carry 1-6 rows), (4) affinity/profile-based residency only after (1) puts you near fit — then prefer a SHARED static profile over partitions. Do not build class-partitioned residency.
5f. CAPACITY ARM MEASURED ON PROD (3090, 2026-11-05): `--expert-cache 4068 -> 5800` raises the fill from 5302 to **7581 blobs (10.09 -> 14.38 GiB = 110 -> 158 slots/layer)**; VRAM used 19.85 -> 23.4 GiB of 24.5. Same-instrument forkbench (400-token caps), batch1 held constant: N=1 86.8 -> **93.4**, N=2 49.8 -> **55.1**, N=4 73.9 -> **79.4**, N=8 53.0 -> **56.0** — +6 to +11% at every concurrency point, shape unchanged. Note the engine's fill count exceeds the `--expert-cache` number (it self-limits to VRAM that fits); read the `filling the GPU's expert cache (N experts, X GiB)` line for the true count, never the flag value.
   - BATCH SLOTS AT THIS CAPACITY (bench_quick.py, 400 tok / reasoning 64, same instrument): batch1 = 119.7 / 50.6 / 46.4 / 44.4 tok/s at N=1/2/4/8; batch2 = 66.5 / 45.4 / **55.2 / 51.5**; batch4 with `--batch-mtp` = **collapse** (1.5-1.8 tok/s per stream, requests cancelled at 68 s, hit 93.5%). Rule: **batch slots pay only at N>=4 (+16-19% vs batch1) and cost ~-44% at N=1**; `--batch-mtp` multiplies window rows (slots x (1+spec), i.e. 4 slots -> ~20 rows/window), so per-window expert demand jumps past 158 slots/layer and the cache thrashes. For a provider serving 1-3 agent streams, batch 1 is correct. `--batch-mtp` + high batch is only viable once slots/layer approaches the union demand (~200-330/layer).
   - KV-side capacity knobs DO NOT add slots on this config (tested): `--kv-grow` left the fill identical (7581 experts / 14.38 GiB both arms) because `--kv-resident 8192` already streams the whole K/V in pinned RAM — there is no up-front 200k KV reservation left to convert. So trimming `--max-context` for slot gain is pointless here; ctx only caps context length. Reverted; prod does not run --kv-grow.
   - BENCH NOISE: at N>=4 the same config measured N=4 = 61.7 then 88.7 tok/s on consecutive passes (±40%); N=1 is stable to ~5% (109-120). Adaptive residency warms during a session, so any N>=4 comparison needs 2-3 passes or it will read noise as signal. Instrument kept at `scripts/bench_quick.py` (400-token completions, reasoning budget 64, N=1/2/4/8).
   - Prod shape now: batch1, ec 5800, ctx 200000, --kv k8v4, --kv-resident 8192, --vram-reserve-mib 500, --expert-profile data/expert-profile.bin. Post-restart probe: 153 tok/s at 97.7% hit.

## 12 GB node (RTX 3080 Ti, iq3_xxs, adopted per-layer package) concurrency arms

Same instrument (`scripts/bench_quick.py`, 400 tok / reasoning 64), two warmed passes per arm; port 8080 = shipped engine, 8081 = locally built experimental engine on the same card (never run both at once on one 12 GB card).

| arm | slots/layer | N=1 | N=2 | N=4 | N=8 agg | N=8 per-stream |
|---|---|---|---|---|---|---|
| shipped 0.1.55 baseline (2 passes) | 44 (2112) | 76.3 / 78.3 | 58.6 / 59.7 | 57.3 / 62.6 | 56.5 / 62.7 | 13.6 / 13.9 |
| control, same args, newer engine | 44 (2112) | 74.9 | 56.0 | 56.3 | 57.4 | 12.0 |
| `--batch 4` | 28 (1344) | 63.1 | 48.0 | 51.3 | 47.7 | 8.8 |
| `--vram-reserve-mib 400` | 49 (2352) | 76.6 / 77.0 | 60.2 / 59.7 | 59.6 / 62.1 | 61.4 / 60.7 | 14.8 / 13.9 |

Verdicts:
1. **Engine minor-version bumps are neutral** on the concurrency curve — the newer-engine control sat inside the shipped baseline band at every N. Version-upgrade claims need a same-card control arm, not a cross-day baseline comparison.
2. **Batch rows are paid for out of expert capacity on 12 GB.** 3 extra rows cost 768 blobs of residency (~450 MiB/row of row state). Cache 2112 -> 1344 slots (44 -> 28/layer), hit 72.9/81.8% -> 58.6/68.9%, and every N point fell. Batch 4 is net-negative on a 12 GB card even though the same bump helps on a slack-VRAM card at N>=4.
3. **Freed VRAM -> slots -> throughput is real but linear and weak** (+11% slots -> +3-6% at N>=2). `--vram-reserve-mib` is the lever that works; the headroom it spends is not free — the node has logged `prefill: device buffers for a chunk of 1024 tokens do not fit (46 of 11903 MiB free)`, so keep reserve >=400 and watch for that line after any capacity gain.
4. **The 12 GB wall is miss traffic.** Aggregate is flat 56-63 tok/s from N=2 through N=8 while single-stream sits 75-78, which is the signature of streaming/CPU-draining ~83 experts (145 MiB) per token rather than any scheduler limit. Thread knobs, prefill chunk, batch rows, MMQ and KV knobs are all measured no-ops against this wall; only slots/layer (linear) and bytes/blob (multiplicative) move it.
5. Non-expert VRAM on this node is ~11.9 GiB and mostly NOT reclaimable: `--kv-resident` is already at its 20480 minimum (KV fully streamed in pinned RAM, so `--max-context` costs no expert slots), `--conversation-cache-mib` is host RAM not VRAM, and the draft head costs only ~198 MiB here (the ~0.9 GiB the help text advertises is a different model). Budget ~200 MiB, not 900 MiB, for dropping the MTP/draft layer on this architecture.
6. `--pcie-frac` (present in the live prod arg line) is undocumented in the newer engine's help and prints no effect line — treat it as cruft and drop it on engine adoption.
