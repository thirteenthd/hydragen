## Triton w8a16 grouped MoE on sm_86 (microbench validated, cos=1.0)
- sm_86 Triton blocks fp8e4nv in the compiler wholesale: loading a float8_e4m3fn tensor directly fails (`type fp8e4nv not supported in this architecture`) and even a uint8->fp8e4nv bitcast cast is refused. Working path: pass weights as `.view(torch.uint8)` and DECODE e4m3 bits in-kernel so no fp8 dtype enters the IR: `i=u.to(tl.uint32); s=(i>>7)<<31; e=(i>>3)&0xF; m=i&7; bits=s|((e+120)<<23)|(m<<20); normal=bits.to(tl.float32, bitcast=True)`, subnormal (e==0) = ±m*2^-9. Exact vs torch fp8->float (maxdiff 0.0).
- Validated kernel: A [E_u,M,K] bf16 (row block per expert), W [E_u,N,K] uint8, S [E_u,N/128,K/128] f32 block scales, VALID [E_u] int32 rows-per-expert mask; grid (N//128, cdiv(Mpad,BM), E_u); BLOCK_N must equal the 128 scale-block width so one scalar scale loads per (pid_n, k0//128); dequant W in f32, mult scale, cast bf16, `tl.dot(a, tl.trans(w_tile))` when the tile loads as [BLOCK_N, BLOCK_K]. 3080 Ti: 13.2 us/expert at M=1, ~250 GB/s — 1300x the eager host-dequant path (~17 ms/expert); matches the 3090 bmm microbench (14 us/expert) so Ampere Triton closes the same kernel-structure gap.
- Kernel-construction traps (each cost one debug cycle): use ONE offset form inside the k-loop — with `kk = k0 + offs_k` in the loads, do NOT also seed base pointers with offs_k or advance them by BLOCK_K per iteration; the double-advance reads past K and is invisible at K<=BLOCK_K (single-block probe passes, real shapes fail). Masks/flags defined inside the loop body are not visible after it in the Triton frontend — hoist above the loop.
- Debug kernels with a controlled probe ladder, not full shapes: one expert, K=256 (2 k-blocks) with controlled scale blocks [1,1]/[1,2]/[2,1] isolates k-scale indexing; N=256 isolates n-block indexing; then a full-shape cosine check vs an fp32 reference. Zero-fill the output buffer before comparing — `torch.empty` garbage reads as NaN and masquerades as kernel NaN.
- Microbenching while a server holds the GPU: free it first; over ssh use the bracket trick `pkill -f "launch[_]server"` — the unbracketed pattern matches the remote shell's own command line (ssh exits 255, the session dies, the server survives). Keep kill and relaunch in SEPARATE ssh calls — a combined `pkill ... launch_server...` line self-matches: the pkill kills its own wrapper before the launch runs.
- Long server boots: launch `nohup ... > log 2>&1 & echo PID=$!` inside ssh, poll the log in later calls for markers (`fired up and ready` / `Scheduler hit an exception`); anchor CRASH detection on `Scheduler hit an exception`, not bare `Traceback|Error` — benign warnings (TileLang data race) carry both words and produce false CRASH hits; never a foreground `sleep N; ssh` with N near the tool timeout. Cold-cache shard load ~14 s/it vs ~2.2 s/it warm.
- INTEGRATION VERIFIED (banked §24): `pyhook/hydragen_moe_triton.py`, env `HG_TRITON_MOE=1`, `HG_MOE_CACHE_N`: replaces PagedExpertsMoEMethod.apply with host-store gather of RAW fp8+scales into a per-layer device cache, two launches of this kernel (gate/up, then down), silu*up + weighted sum in torch. The apply decision tree it replaces: `device_executor.run` whenever topk_ids.numel() <= num_resident, else the wave `executor`; both bottom out in the base quant method's Triton kernel — the dtype-dependent part is only that kernel, residency/waves are dtype-agnostic. Serving result: warm 16-token run 0.56 s/token (15x eager), first token = oracle parity; kernel recipe, slot-table freeing and VRAM budget in references/ampere-triton-w8a16.md.
- Staging-cache design rules for the apply shim (KeyError: staged expert evicted mid-call before the stack was built): stage every expert of the call into a LOCAL dict, build `torch.stack` from that dict, and only THEN insert fresh entries into the bounded per-layer FIFO cache; eviction may only pop keys not in the current call's set. Keep the cache cap independent of per-call U — a prefill call routes many unique experts (U up to ~60) and a naive cache grows by U x 5.6 MB x 48 layers = multi-GB VRAM blowup. Never `.item()` per routed row inside the row-mapping loop (GPU sync per row) — count rows in python, build the VALID int32 tensor once.
- VRAM budget: the persistent device cache is PER LAYER (~5.6 MB x N x 48) but the server at mem-fraction 0.95 leaves only ~200-600 MB free — banked shape is HG_MOE_CACHE_N=1. Do NOT lower --mem-fraction-static to make headroom on a hybrid model: the mamba/GDN state cache is sized from it and 0.85 dies with `Computed max_mamba_cache_size=-6`; free the dead native K-slot table (~2.7 GB at K=10) in the first shimmed apply instead.
- M2-Real correctness banked: greedy "The capital of France is" -> first token Paris, matching the M1 oracle target; 16-token continuation coherent.

## M3 concurrency verdict (2026-11-08, §25): staging-bound, GEMM idle

- HG_MOE_PROF=1 shim instrumentation prints per-layer stage/gem/glue every 8 calls per layer (`self._hgp_*`; note print gate is per-layer-instance steps, use small modulus).
- Warm B=1: stage 8-9 ms/layer, gem 0.3-0.4 ms, glue ~0. MoE staging = 1.9 GB/token at ~5.6 GB/s effective. GEMM idle.
- LRU cache N sweep: N=4 B4 agg 1.29 tok/s, N=6 1.43, N=8 OOM (9.8 GB alloc + 160 MB prefill peak; weights 8.9 + KV/mamba static at mem 0.95 leaves <1 GB headroom for device cache; cache VRAM = 48 layers x N x 5.6 MB).
- Cross-step LRU reuse is weak (miss 7-9 of U=10): router working set churns per token. Vectorizing gather/scatter (index_copy_/index_add_, one .cpu() sync) changed nothing — overhead was never binding.
- Slot-free DOES work: each apply frees ~40 MB/layer (0.04 GB per call, 2.2 GB total across 48 layers); "freed: 10.08 -> 10.04" per-call deltas are correct, do not misread as failure.
- B=4 concurrency gives NO win over B=1 on naive substrate (1.43 vs 1.5 tok/s) — next lever = dedicated bounded host hot-tier + batch affinity (Phase-1 tr18 winner: tier20 hit .850), NOT bigger LRU, NOT python micro-opt.
- Page-cache contention is the real ceiling: PLE mmap 47.7 GiB + store 113 GB vs 62 GB RAM — host reads mostly NVMe misses. Explicit pinned/registered hot-tier budget needed (same lesson as Phase-1 pinned-tier fix).

- The transformers Qwen4Exp builder HARD-REQUIRES the indexer_* config fields (the QSA indexer is always constructed on full-attention layers) — do not drop them from the builder config to disable QSA; the build fails.
- The sglang PLE loader expects `ple.ple_embedding.ngram_embedding.shard_N.weight` SHARDED layout; a builder that writes one unsharded PLE tensor is rejected with "unsupported PLE weight layout". Real checkpoints carry the shards.
- Post-build config edits that change module presence (e.g. ple_layer_ids -> []) leave stranded tensors in the saved checkpoint -> load_weights ValueError. Change the builder and REGENERATE the mini checkpoint; never reconfigure a built checkpoint in place.

## M5 step itemization (HG_STEP_TRACE): the decode step is COPY-bound, not compute-bound
- Recipe: inside the step-profiler wrapper on ModelRunner.forward, fire `torch.profiler.profile(activities=[CPU,CUDA])` around forwards at fixed call indices (e.g. #40,#72 inside a 64-token request) and print `key_averages().table(sort_by="self_device_time_total")` + a second pass sorted by `self_cpu_time_total`. Env-gated (HG_STEP_TRACE=1) so it costs nothing normally. This splits "unaccounted" forward time kernel-by-kernel without touching site-packages.
- Measured decode bs=1 breakdown (3080 Ti, HTIER=64 + fp8 head): Self CUDA total 208 ms = aten::copy_ 171 ms (Memcpy HtoD Pinned 102 + Pageable 64) vs ALL GEMMs ~28 ms (mm 11 + _hg_gemm_e4m3 9.5 + cutlass/bf16 ~8) vs GDN/elementwise/cat ~15 ms. The "135 ms non-MoE overhead" from forward averaging was mostly HIDDEN COPY TIME, not attention cost — do not chase attention kernels before reading the copy table.
- Rule: a `Memcpy HtoD (Pageable -> Device)` row in the profiler table means some host source tensor was NOT pinned — pageable HtoD both runs ~2-3x slower AND stalls the CPU dispatch loop (aten::copy_ ate 942 ms CPU total this way). Fix by materializing quantized/host weight caches with `torch.empty_like(..., pin_memory=True)` + copy once at quant time (the fp8 head wq/scale were exactly this: 64 ms pageable -> ~35 async).
- Pinned 102 ms H2D (1.9 GB/token) at N=6 is the PCIe floor — only levers below it are fewer bytes on the wire (bigger device cache, or quantized-expert diet), never scheduling.
- VRAM ceiling CONFIRMED: HG_MOE_CACHE_N=10 OOMs (10.19 GB alloc, 26 MiB free) even with diet + slot-free; N=6 (1.58 GB cache) is the hard ceiling at mem-fraction 0.95 on 12 GB with this static pool. Do not re-litigate N>=8 on this card/config.

## §31-32 pinned head banked + side-stream staging NO-WIN + greedy nondeterminism
- §31 (pinned fp8 head at N=6): lm_head 73 -> 33.1-33.2 ms/step just by materializing the quantized wq/scale into `pin_memory=True` buffers once.
